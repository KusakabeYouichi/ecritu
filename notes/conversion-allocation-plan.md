# 変換の一時確保を断片化させない計画(未着手)

起案: 2026-09-15(edition 2936 時点)。**着手前にこの文書の「測り直す」を必ず実施すること。**

## 何が起きているか

footprint は「生きたデータ」ではなく **malloc アリーナ全体**を数える。アリーナは使用量が
天井に近づくたび段で増え、OS へは返らない。実機 1 セッション(41 分・変換 663 回)の実測:

| 時刻 | 生きたデータ | アリーナ | footprint |
|---|---|---|---|
| 開始 | 24MB | 52MB | 37.8MB |
| 28 分後 | 29.0MB | 56MB | 43.2MB |
| 37 分後 | 30.4MB | 64MB | 45.6MB |
| 40 分後(ピーク) | 33.7MB | 64MB | 51.0MB |

`malloc_zone_pressure_relief(nil, 0)` は既に毎回呼んでおり、**返却量はゼロ**。空きが連続して
いないことの直接の証拠。キーボードを閉じるたびのスリム化で使用量は下がる(32.4→30.4MB)が
アリーナは 64MB のまま動かない。

## 断片の主犯

`MultiClauseNode` が `surface` と `reading` の 2 つの `String` を持つ。11 かなの入力 1 回で
**329 ノード**立ち、さらに DP 全体で一時 String が数千個生まれる(コード注記 2560 参照)。
小さな確保が大量に散るのでアリーナが縮められない。

## 却下した案: 変換専用の確保ラッパー

「変換中だけ専用プールから確保し、終わったらプールごと返す」は筋としては正しいが、
**Swift では主犯を捕まえられない**。`String`/`Array`/`Dictionary`/クラス実体はランタイムが
既定ゾーンへ直接確保し、呼び出し側でゾーンを差し替える手段が無い。自前ゾーン
(`malloc_create_zone`)で扱えるのは自分で生バイト列として確保したものだけなので、
先に下の案 1 をやらない限り成立しない。案 1 を済ませれば大きな確保は large 経路に載って
解放時にページが返るため、専用ゾーンを足す意味はほぼ無くなる。

## 案 2(先にやる): 大きな緩衝を使い回す

ノード配列・コスト配列・作業用 Set を変換器の持ち物にし、`reserveCapacity` で一度だけ伸ばして
以後は中身を空にするだけにする(`removeAll(keepingCapacity: true)`)。

- 変換の意味論を触らないので回帰の危険が小さい。
- 効果は「ピークは 1 回で済み、以後は増えない」まで。既に散った断片は消えない。
- 測り方: 実機で 30 分ほど使い、`alloc` が 52MB から動かないことをログで確認する。

## 測り直し(2026-09-18 13:56〜14:07 JST、edition 3076、学習リセット・変換キャッシュクリア後、メモ 11 分)
| 時点 | 生きたデータ | アリーナ | footprint |
|---|---|---|---|
| 起動(個体表示後) | 13.6MB | 36MB | 26MB |
| 最初の変換(20 秒以内) | 17.7〜20.0 | 40→44 | 32〜33 |
| 11 分後(変換 386 回・確定 184 字) | 20〜22 | **44(不動)** | 34〜37 |
高水位台帳は #6(44MB、起動 20 秒後)が最後で、以後の 11 分間に一度も増えていない。旧計測(起動 52 → 37 分後 64、
fp 51)と比べ、アリーナは 20MB 低く、セッション中の階段成長が消えた。効いたのは補助語彙の mmap 化(3030)、
LM/word_costs キャッシュの 2 世代化(全消し→作り直しの山が無くなった)、整数 ID 化(遷移内の一時 String が消えた)
の組み合わせと見る。残るスラック(アリーナ 44 − 生きたデータ 21 ≈ 23MB)は起動時の領域確保と半端な領域で、
実害(fp 34〜37、上限 77)は無い。**案 2・案 1 の最終段は、より長いセッション(1 時間級)で階段が再発しない限り保留**。

## 案 1(本命): 文字列を整数 ID に置き換える

表層と読みを一度だけ配列へ intern し、DP の中は `Int32` の添字で回す。辞書のキーも Int にする。

- 1 回の変換の確保が「小さな塊が数千個」から「大きな配列が数個」に変わる。
- 大きな確保は malloc の large 経路に載り、解放時にページが OS へ返る。断片化自体が消える。
- 中核の書き換えになるので、案 2 で足りるかを見てから判断する。
- 触る範囲: `KanaKanjiConverter+MultiClause.swift` の DP 本体、`MultiClauseNode`、
  `transitionCost` の各種表引き(表は読み/表層の String キーなので境界で変換が要る)。

## 返せないもの

LM の単語頻度・連接頻度のキャッシュは意図して変換をまたいで生かしている(実測で 1 セッション中に
連接 1094→4132 件)。これは断片ではなく生きたデータなので、どの案でもプールの外に残る。
「変換していないときは全部返却」にはならない。

## 実機での検証と測り直し(2026-09-24、edition 3199〜3200)

### 結論

- **案 1 最終段(ノードの String を表へ)は実施しない。** 09-18 の計測どおり主犯ではなく、今回の
  実機データでも「アリーナが伸び続ける」現象自体が単一インスタンスでは起きていない。
- footprint の実害は**多重生存の滞留**であって、変換の一時確保ではない。次に 45 が出たら、まず
  センサス(alive=N)と `忘れられた離脱個体の掃除を完了` の行を見る。
- この文書の残件は「3199 の掃除が入った状態で、17 分級の多重生存セッションでも fp が 40 未満に
  収まるか」の 1 点。

## 案 2 の続き(2026-09-24 午前、edition 3201)

朝の実機ログで、50 分・変換 746 回のセッション中にアリーナが 48→52→60MB と伸びた(生きたデータは
21〜25MB で横ばい)。**長いセッションではラチェットが再発する**ことが確定したので、断片を作る側の
確保を減らした。方針は「小さく散らす確保を減らす」ではなく「**中くらい(2KB〜16KB)の確保の churn を
減らす**」— 4MB 刻みの伸びを起こすのはこの層で、`≤1K` の小片は既存の空きに収まる。

`ALLOC_CENSUS_MIN_SIZE=2048` + `_STACKS=1` で上位を取り、次の 5 か所を直した。

| 直した場所 | 何をしていたか |
|---|---|
| `candidateInflectionRuleIndices(forReadingEndingWith:)` | 末尾文字だけの純関数なのに、呼ぶたびに添字列を併合して新しい配列を作っていた。区間ごとに呼ぶので打鍵あたり 4KB 超が 3 個。**末尾文字ごとに前計算した表**へ |
| `TwoGenerationCache.set` | 世代の 1 本目だけ `reserveCapacity` が無く、空から rehash で育っていた(長寿命側が穴を開ける) |
| `wordLMUnigramCosts(for:)` / `candidateMinWordCosts(for:)` | 結果 `[String: Int]` と未取得リストを挿入で育てていた(`_copyOrMoveAndResize` が打鍵あたり 3 個) |
| `wordLMBigramCostsAligned(for:)` | `uncachedIndices` の append 成長と `map` の中間配列 |
| `candidatesForReading` | `a + b + c` の連結で中間配列を 2 本作っていた |

### 効果(-O、打鍵 1 回あたり)

| | 着手前(3200) | 3201 |
|---|---|---|
| 確保回数 | 1,246 | 1,241 |
| 総バイト | 354KB | **325KB(−8%)** |
| **2〜16KB の確保** | **50** | **43(−14%)** |
| DP 段のバイト | 26KB | 13KB |
| 単文節の一時ピーク | 16KB | 6KB |

回数がほぼ同じなのは、成長列(4→8→16…)を 1 回の確保に畳んだぶんと、測定のばらつき(±10)が
相殺しているため。**狙いは回数ではなく中くらいの塊の入れ替わり**なので、そこが 14% 減ったのが本体。

**実機での確認待ち**: 50 分級のセッションでアリーナが 60MB まで伸びるかどうか。伸びなければ効いた、
伸びるなら次は供給段が返す結果配列そのもの(区間ごとに 165 本)に手を付ける必要がある。
