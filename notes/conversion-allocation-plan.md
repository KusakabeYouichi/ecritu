# 変換の一時確保を断片化させない計画(未着手)

起案: 2026-09-15(edition 2936 時点)。**着手前にこの文書の「測り直す」を必ず実施すること。**

## 何が起きているか

footprint は「生きたデータ」ではなく **malloc アリーナ全体**を数える。アリーナは使用量が
天井に近づくたび段で増え、OS へは返らない。実機 1 セッション(41 分・変換 663 回)の実測:

| 時刻 | 生きたデータ | アリーナ | footprint |
|---|---|---|---|
| 開始 | 24MB | 52MB | 37.8MB |
| 28 分後 | 29.0MB | 56MB | 43.2MB |
| 37 分後 | 30.4MB | 64MB | 45.6MB |
| 40 分後(ピーク) | 33.7MB | 64MB | 51.0MB |

`malloc_zone_pressure_relief(nil, 0)` は既に毎回呼んでおり、**返却量はゼロ**。空きが連続して
いないことの直接の証拠。キーボードを閉じるたびのスリム化で使用量は下がる(32.4→30.4MB)が
アリーナは 64MB のまま動かない。

## 断片の主犯

`MultiClauseNode` が `surface` と `reading` の 2 つの `String` を持つ。11 かなの入力 1 回で
**329 ノード**立ち、さらに DP 全体で一時 String が数千個生まれる(コード注記 2560 参照)。
小さな確保が大量に散るのでアリーナが縮められない。

## 却下した案: 変換専用の確保ラッパー

「変換中だけ専用プールから確保し、終わったらプールごと返す」は筋としては正しいが、
**Swift では主犯を捕まえられない**。`String`/`Array`/`Dictionary`/クラス実体はランタイムが
既定ゾーンへ直接確保し、呼び出し側でゾーンを差し替える手段が無い。自前ゾーン
(`malloc_create_zone`)で扱えるのは自分で生バイト列として確保したものだけなので、
先に下の案 1 をやらない限り成立しない。案 1 を済ませれば大きな確保は large 経路に載って
解放時にページが返るため、専用ゾーンを足す意味はほぼ無くなる。

## 案 2(先にやる): 大きな緩衝を使い回す

ノード配列・コスト配列・作業用 Set を変換器の持ち物にし、`reserveCapacity` で一度だけ伸ばして
以後は中身を空にするだけにする(`removeAll(keepingCapacity: true)`)。

- 変換の意味論を触らないので回帰の危険が小さい。
- 効果は「ピークは 1 回で済み、以後は増えない」まで。既に散った断片は消えない。
- 測り方: 実機で 30 分ほど使い、`alloc` が 52MB から動かないことをログで確認する。

## 案 1(本命): 文字列を整数 ID に置き換える

表層と読みを一度だけ配列へ intern し、DP の中は `Int32` の添字で回す。辞書のキーも Int にする。

- 1 回の変換の確保が「小さな塊が数千個」から「大きな配列が数個」に変わる。
- 大きな確保は malloc の large 経路に載り、解放時にページが OS へ返る。断片化自体が消える。
- 中核の書き換えになるので、案 2 で足りるかを見てから判断する。
- 触る範囲: `KanaKanjiConverter+MultiClause.swift` の DP 本体、`MultiClauseNode`、
  `transitionCost` の各種表引き(表は読み/表層の String キーなので境界で変換が要る)。

## 返せないもの

LM の単語頻度・連接頻度のキャッシュは意図して変換をまたいで生かしている(実測で 1 セッション中に
連接 1094→4132 件)。これは断片ではなく生きたデータなので、どの案でもプールの外に残る。
「変換していないときは全部返却」にはならない。
